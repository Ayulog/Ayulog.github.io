## 先分清格式、编码器和容器

| 编码格式     | 本文使用的实现  | FFmpeg 中的名字 | 需要先考虑的事情                                      |
| ------------ | --------------- | --------------- | ----------------------------------------------------- |
| H.264 / AVC  | x264            | `libx264`       | 常见播放设备的支持情况，以及是否需要 8-bit 4:2:0 输出 |
| H.265 / HEVC | x265            | `libx265`       | 目标设备的 HEVC、Main 10 和分辨率支持                 |
| AV1          | SVT-AV1         | `libsvtav1`     | 设备是否能硬件解码，软件解码能否流畅播放              |
| AV1          | libaom / aomenc | `libaom-av1`    | 使用的是另一套实现，参数、预设和速度不能照搬 SVT-AV1  |

MKV、MP4 是容器，可以装入视频、音频、字幕和其他信息。把 MP4 换成 MKV，并不等于把 H.264 变成 HEVC；只换封装、保留原码流的流程见[蓝光 Remux 与封装](/posts/blu-ray-remux/)。

同样写着 H.264、HEVC 或 AV1，也可能调用显卡硬件编码器。硬件编码与 x264、x265、SVT-AV1 的参数和速度取舍不同，不能只凭输出格式判断实际用了哪个编码器。

## 画质、速度和体积怎么取舍

### CRF：先按质量试压

CRF 是按质量控制码率的一种方式。一般来说，数值调低会保留更多细节，也会增加体积；数值调高则更节省空间，但更容易丢失细节。复杂画面需要更多码率，因此它不承诺固定的最终体积。

**不同编码器的 CRF 不能直接比较。** x264 的 18、x265 的 18 和 SVT-AV1 的 18 不是同一档画质。即使使用同一编码器，升级版本、改变预设或处理片源后，也应重新抽样比较。

不知道目标码率时，可以先固定预设，在几段有代表性的画面中寻找能接受的 CRF，再估算完整编码所需时间和空间。不要只看一段明亮、静止的画面就确定全片参数。

### preset：用多少时间换压缩效率

x264 和 x265 使用 `fast`、`medium`、`slow` 等名称；SVT-AV1 使用数字预设，数值越高通常越快。它们控制编码器搜索和决策的投入，不能直接理解成画质百分比。

较慢预设通常有利于在相近画质下节省码率，但耗时可能增加很多。在固定 CRF 下，体积也未必随预设单调变化。应该把画面、体积和耗时一起比较，而不是默认 `placebo` 或最小数字总值得使用。

`tune` 则面向特定素材或目标，例如颗粒、动画、主观观感或某项指标。它会改变一组设置，适合了解其作用后再加；不要把不同教程的 `tune` 和高级参数拼成一条通用命令。

### ABR 与两遍编码：有体积目标时再考虑

ABR 围绕平均码率工作。两遍编码通常先分析，再利用统计信息分配码率，适合有明确容量或平均码率目标的任务。两遍流程必须保持相同的画面输入、顺序、滤镜和对应统计文件，不能将不同片源的统计混用。

粗略估算时，视频平均码率等于可分配给视频的位数除以时长。音频、字幕、附件和容器也会占空间，因此“文件总容量 ÷ 时长”不能直接全给视频。

两遍不是所有 CRF 任务都需要的提质开关。各编码器支持的率控制组合不同，尤其 SVT-AV1 的相关接口经历过变化，具体流程应查所用版本的文档。

### VBV、profile 和 level：满足交付限制

VBV 对码流施加与解码缓冲相关的约束。播放器、广播或流媒体有峰值码率和缓冲要求时，才需要按目标设置相应的最大码率与缓冲大小。它不等于保证文件达到某个平均码率，也不等于保证每个瞬间的码率都相同。

`profile` 限定可使用的编码工具和格式组合，`level` 则约束分辨率、处理速率、码率等能力要求。它们的用途是让码流符合接收端要求，数值更高不会自动让画面更好。

这些限制可能影响编码器分配码率的自由度。没有设备规范时，不必先抄一组严苛的 VBV 或 level；有明确交付要求时，也不能只改标签而不检查实际码流是否符合要求。

## 高级参数按问题分组

长命令可以先按下面的用途拆开。表中的同类设置并不代表 x264 与 x265 有相同的取值范围和实现，具体含义仍要分别查文档。

| 想调整的事情                 | 常见参数                                                | 怎样理解和比较                                                                                                 |
| ---------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 不同复杂度画面之间的码率分配 | `qcomp`                                                 | 调整量化曲线的压缩程度，与率控制及时间相关分配共同作用；不能仅按“动作片／剧情片”决定一个值                     |
| 同一帧不同区域的量化分配     | `aq-mode`、`aq-strength`                                | AQ 会根据画面分析调整区域量化，比较暗部、平坦渐变和纹理是否获得合理保留；强度不是整体画质滑块                  |
| 考虑后续帧对当前画面的引用   | x264 的 `mbtree`、x265 的 `cutree`，以及 `rc-lookahead` | 利用时间相关性分配码率，预读也参与帧类型和转场判断；关闭树分配不是通用提质措施，增加预读还会影响延迟和资源占用 |
| 参考关系与关键帧安排         | `ref`、`bframes`、`b-adapt`、`keyint`、`min-keyint`     | 影响预测、随机访问、耗时及兼容性；日志中的连续 B 帧比例可辅助诊断，不能用固定百分比证明参数最优                |
| 运动估计的搜索投入           | `me`、`merange`、`subme`                                | 分别涉及搜索方法、范围和子像素精细化等工作；增加搜索可能更慢，`subme` 不是锐化滤镜                             |
| 编码决策与量化的率失真分析   | x265 的 `rd`、`rdoq-level`，x264 的 `trellis`           | 在码率代价和失真之间做决策；不同开关作用于不同阶段，不是可以互相替代的“质量等级”                               |
| 主观观感的取舍               | `psy-rd`，以及 x265 的 `psy-rdoq`                       | 改变决策对纹理和能量保留的偏向，也可能增加码率或带来伪影；同时看细节、颗粒与边缘，不能只看锐利程度             |
| 编码环路中的滤波             | `deblock`，以及 x265 的 `sao`                           | 处理编码重建中的块边界或偏差；它们与前处理降噪不同，不能按“真人固定某值”或“一律关闭”决定                       |

高级参数还存在生效条件。例如 x265 的 `psy-rdoq` 需要 `rdoq-level` 为 1 或 2；将后者设成 0，再提高前者不会产生预期效果。x265 的 `psy-rd` 也要使用基于率失真的模式决策，即 `rd` 至少为 3。两者的定义见[官方参数表](https://x265.readthedocs.io/en/master/cli.html)。

x264 的 AQ 3 带有向暗场倾斜的设计，不能由此推导它对所有片源都最好；`no-fast-pskip`、`no-dct-decimate` 等开关也不应在不了解作用时全部追加。先从预设建立基准，再针对可见问题测试，比一次覆盖几十个选项更容易判断变化来自哪里。

另外两种常见混淆也需要分开：**x265 的 `high-tier` 是 HEVC 等级约束的一部分，与 CPU 是否支持 AVX2 无关**；**x264 的参考帧限制要结合 level 和画面尺寸判断，不是所有分辨率都固定最多 4 帧**。CPU 指令集、解码端能力和编码标准约束是不同的问题。

`tune grain` 则是面向颗粒素材的一组设置。[x265 的预设与 tune 文档](https://x265.readthedocs.io/en/master/presets.html)说明，它会限制帧内、帧间的量化变化，以减少颗粒分布不均造成的明显伪影；它不是“任何素材的最高画质模式”。选定 tune 后再覆盖其中参数，也可能破坏原本的配合关系。

## 位深与播放兼容性

8-bit、10-bit 是位深；4:2:0、4:2:2、4:4:4 是色度采样。它们与分辨率、帧率和 HDR 是不同概念。本文例子使用常见的 4:2:0 输出，选项写在命令中，便于核对。

- **x264 的 8-bit 4:2:0** 适合先测试常见播放链路。H.264 10-bit 的硬件支持不能照搬 HEVC Main 10 的经验。
- **x265 和 SVT-AV1 的 10-bit** 可以用来比较编码量化误差与色带表现，但要确认编码器构建和播放器支持。
- **8-bit 输入转成 10-bit 输出** 不会恢复源文件中已经丢失的层次，也不能修复所有色带。
- **10-bit 不等于 HDR。** HDR 还涉及传递函数、色彩原色及可能的静态或动态元数据。

如果源文件是 4:2:2、4:4:4、HDR、Dolby Vision，或者具有特殊色彩要求，下面的例子就不适合直接套用。像素格式转换本身也会改变数据，需要单独设计处理和验证流程。

## 准备同一段测试片

以下示例限定为**已确认逐行、恒定帧率（CFR）、SDR 的普通 4:2:0 素材**。它们截取第 5 分钟起的 30 秒，只编码第一条视频流，用于比较视频画面；源片不够长时，改成确实存在的片段。

示例不处理反交错、逆胶卷、VFR 时间戳、HDR 或 Dolby Vision，也不保证音轨、字幕、章节、附件和全部元数据的保留。正式成品需要另走封装和检查流程。

先确认 FFmpeg 包实际包含对应编码器：

```sh
ffmpeg -version
ffmpeg -h encoder=libx264
ffmpeg -h encoder=libx265
ffmpeg -h encoder=libsvtav1
```

FFmpeg 的版本号和它链接的编码库版本不是一回事。下载了独立的新版 `x265` 或 `SvtAv1EncApp`，也不会自动更新现有 FFmpeg 里的库；以帮助输出及编码开始时的日志为准。

用 MediaInfo 或 ffprobe 检查源片，再结合画面与必要的逐帧信息判断：

```sh
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,pix_fmt,field_order,r_frame_rate,avg_frame_rate,color_range,color_space,color_transfer,color_primaries -of default=noprint_wrappers=1 input.mkv
```

这些字段是检查线索。平均帧率与标称帧率相同，并不能单独证明整个文件都是 CFR；字段缺失也不代表可以随意补成 BT.709。遇到片源信息和实际画面不一致，先回到片源分析。

## x264：先走通 H.264 流程

```sh
ffmpeg -ss 00:05:00 -i input.mkv -t 30 -map 0:v:0 -an -sn -dn -c:v libx264 -preset slow -crf 18 -pix_fmt yuv420p test-x264.mkv
```

这里的 `slow` 和 CRF 18 只是试压起点，`yuv420p` 表示 8-bit 4:2:0。`-map 0:v:0` 选择第一条视频流，`-an -sn -dn` 明确排除音频、字幕和数据流；输出没有声音是预期行为。

x264 的首要来源是 [VideoLAN 项目页](https://www.videolan.org/developers/x264.html)和[官方源码仓库](https://code.videolan.org/videolan/x264)。独立程序可以运行 `x264 --fullhelp`；FFmpeg 的 `-preset`、`-crf` 则属于它对库的封装接口，高级参数需查 [FFmpeg 的 libx264 说明](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb)。

旧教程可能针对特定修改版、单独的 8-bit 或 10-bit 构建。是否能直接读某种容器或脚本，取决于编译时启用了哪些输入模块，不能只根据文件名都是 `x264` 就假定功能相同。

## x265：核对构建和输入方式

```sh
ffmpeg -ss 00:05:00 -i input.mkv -t 30 -map 0:v:0 -an -sn -dn -c:v libx265 -preset slow -crf 20 -pix_fmt yuv420p10le test-x265.mkv
```

这次使用 10-bit 4:2:0 输出。CRF 20 不表示它与上面 x264 的 CRF 18 画质相同；只是分别给出一个可开始比较的设置。也不要仅凭结果更小，就判断 x265 在这次试验中保留了更多细节。

[x265 官方参数文档](https://x265.readthedocs.io/en/master/cli.html)明确说明：原版独立 CLI 的输入是 raw YUV 或 Y4M。它不像 FFmpeg 那样默认负责打开任意视频容器；从 VapourSynth 接入时，通常先通过 `vspipe` 输出 Y4M，再送给编码器。

独立 CLI 的 `--output-depth` 还需要对应位深的库支持。FFmpeg 中使用 `-pix_fmt yuv420p10le`，最终是否支持仍要检查构建和编码日志。

[x265 Mod by Patman](https://github.com/Patman86/x265-Mod-by-Patman) 是第三方增强构建。仓库 README 列出的扩展包括进度显示、Y4M 的 `XLENGTH` 标记，以及加载外部 AviSynth / VapourSynth 库。它可以方便特定工具链，但不应据此推导出“同参数必然比上游画质更好”。

使用增强版时，记录完整版本和来源，将上游参数与扩展功能分开。网页上的独立 CLI 参数也不一定能原样写进 FFmpeg；后者另有 [libx265 接口说明](https://ffmpeg.org/ffmpeg-codecs.html#libx265)。

## AV1：先明确使用哪一个实现

下面使用 SVT-AV1，方便和前两条命令采用相同的 FFmpeg 输入与输出方式：

```sh
ffmpeg -ss 00:05:00 -i input.mkv -t 30 -map 0:v:0 -an -sn -dn -c:v libsvtav1 -preset 6 -crf 30 -pix_fmt yuv420p10le test-av1.mkv
```

这里的 preset 6 和 CRF 30 同样不是质量承诺。SVT-AV1 的数字预设越低通常投入越多计算；先确认耗时能够接受，再围绕目标画质调整 CRF。播放检查还要包括实际目标设备的解码负载、拖动和掉帧情况。

### SVT-AV1 与 aomenc

[SVT-AV1](https://gitlab.com/AOMediaCodec/SVT-AV1) 是一套 AV1 编码器实现，提供独立程序 `SvtAv1EncApp`，FFmpeg 对应 `libsvtav1`。这里的 GitLab 地址仍是 README 明确标出的官方主地址。

`aomenc` 是 [AOM 的 libaom 项目](https://aomedia.googlesource.com/aom/)提供的命令行编码工具；在 FFmpeg 中使用的是 [`libaom-av1`](https://ffmpeg.org/ffmpeg-codecs.html#libaom_002dav1)。例如它使用 `cpu-used` 调节速度取舍，不能把 SVT 的 `preset` 数字和整串参数照搬过去。

选择实现时，应比较自己的素材、机器和允许耗时。AV1 是格式名，不能仅凭它推出所有 AV1 编码器具有相同的速度、画质和参数含义。

### 参数表要对应调用接口

截至核查日，SVT-AV1 v4.2.0 的[参数表](https://gitlab.com/AOMediaCodec/SVT-AV1/-/blob/v4.2.0/Docs/Parameters.md)允许独立程序的 `--crf` 使用 1–70，并支持 0.25 步进；[FFmpeg 的 libsvtav1 文档](https://ffmpeg.org/ffmpeg-codecs.html#libsvtav1)及当前实现中，`-crf` 仍是 0–63 的整数接口。两份文档说的是不同入口。

FFmpeg 还提供 `-svtav1-params key=value:key=value` 向库传参数，但可用项仍受所链接的 SVT-AV1 版本限制。不要把官网最新参数直接追加到旧软件中，也不要在多个入口重复设置同一选项而不检查生效结果。

SVT 的[官方 FFmpeg 指南](https://gitlab.com/AOMediaCodec/SVT-AV1/-/blob/master/Docs/Ffmpeg.md)指出，FFmpeg 5.1 起才具备较完整的 SVT 参数透传能力。这个信息用于辨认旧教程；实际使用仍应优先选择当前维护的构建。

### film grain 需要单独比较

AV1 的颗粒合成机制可以用较少的信息描述颗粒特征，在解码时重建颗粒。它保留的是视觉特征，不能等同于逐像素保留源颗粒，更不是给所有画面加细节的开关。

SVT-AV1 中的 `film-grain` 与 `film-grain-denoise` 有不同职责。v4.2.0 参数表里，后者默认是 `0`；只看到旧教程写“开启颗粒就会先去噪”，不足以判断当前版本的完整行为。过强处理可能损失细节，未适当匹配的合成颗粒也可能使画面更脏。

因此基础试压先不加入这些参数。确认片源存在需要处理的颗粒后，再查当前[参数表](https://gitlab.com/AOMediaCodec/SVT-AV1/-/blob/master/Docs/Parameters.md)，分别检查纹理保留、颗粒强度和运动中的稳定性。不要因单帧截图变干净就认定压制更好。

## 怎样比较试压结果

### 先选连续片段，再做分散抽样

试压需要覆盖不同画面，而不只是从全片等间距取几个截图。可以先准备下面几类连续片段，每段给编码器留出足够的前后画面，再对照观看。

| 片段类型                   | 重点观察                                                       |
| -------------------------- | -------------------------------------------------------------- |
| 暗部、阴影、天空或墙面渐变 | 色带、块状变化、原有层次是否丢失                               |
| 头发、织物、树叶和细小文字 | 纹理是否被抹平，边缘是否出现额外振铃或粗糙感                   |
| 平移、快速运动、转场和闪光 | 运动中细节变化、拖影、短时崩坏与恢复过程                       |
| 胶片颗粒或持续噪声         | 连续播放时的颗粒稳定性，有没有忽强忽弱、结块或粘在画面上的感觉 |

按固定间隔拼接很短的片段，可以用来快速扫描问题或粗略估计码率，但拼接点改变了前后帧关系，也可能改变 GOP、转场判断和预读分析。几十帧的小片段无法充分代表整场运动；不要把这种抽样结果当成完整连续编码的精确预测。

修改抽样脚本前，确认它到底跳过哪些帧、保留哪些帧。正式编码时移除取样步骤，并重新确认输出总帧数，避免把测试片当作全片交付。

### 固定条件，一轮只回答一个问题

1. 固定源文件、时间范围、裁切、缩放、滤镜、帧率、色彩转换和输出位深，保存一份基准命令。滤镜一旦变化，就不再是单纯的编码参数对比。
2. 先固定预设，比较 CRF 的变化；找到大致可以接受的画面后，再比较较快或较慢的预设。调整 AQ、psy 或环路滤镜时，围绕已经发现的问题逐项测试。
3. 比画质时，同时考虑输出体积。某个参数在相同 CRF 下“更清晰”，也可能只是使用了更多码率；必要时重新调整 CRF，把体积或主观质量拉到相近条件再比。
4. 比耗时时，尽量固定机器、线程配置和后台负载。片源读取或滤镜可能成为瓶颈；总流程变慢不一定全由编码器造成。差异接近波动范围时再复测，不凭一次小幅差距排名。

比较工具应对齐同一帧，使用一致的缩放、色彩管理和显示条件。静帧便于找细节损失，连续播放则更容易发现闪烁、颗粒变化和运动失真。

每次记录源片段、编码器完整版本、参数、耗时、帧数和输出大小，并给试验片取能区分条件的文件名。写下具体观察，例如“暗部新增块状变化”或“运动纹理更稳定”，比只记“这组更好”更方便复查。

### 日志辅助判断，画面决定是否接受

日志中的 I／P／B 帧数量、平均 QP、平均码率和编码速度可以帮助发现异常，例如某组参数明显增加了码率，或者帧数与预期不符。QP 是量化相关的内部数值，不是直接测得的画质；不同编码器、位深和率控制设置下，不应拿它做统一的画质门槛。

原盘码率的一半、HEVC 体积必须低于 H.264 的某个比例、1080p 固定不能超过某个码率，都只能是特定用途下的个人容量目标。源片复杂度、噪声、时长和可接受失真不同，不存在统一的压缩比例标准。

抽样平均码率可以粗略推算全片体积，但不能承诺误差小于某个固定数值。抽到大量暗场、片尾或动作场景，结果都会偏向这些内容；确定参数后，仍要检查全片的实际输出。

PSNR、SSIM、VMAF 等指标可以帮助定位变化，但会受到缩放、裁切、帧对齐、色彩转换及模型适用范围影响。使用专门针对某项指标的 tune，也会改变结果含义；指标更高不能代替播放检查。

## 从试压到正式成品

试压满意后，才将确定的处理流程应用到完整视频。不要机械复制短片的时间范围；完整编码还要检查片尾、帧数、时长和错误日志。

视频编码不自动完成音频、字幕和章节整理。将新视频与需要保留的原音轨、字幕、章节和字体附件交给 MKVToolNix 等工具封装，核对语言、轨道名称、默认／强制标记及同步情况，操作路线见[蓝光 Remux 与封装](/posts/blu-ray-remux/)。

若中间经过 VapourSynth 或 Y4M 管道，还应核对帧率、色彩信息和最终写入的元数据。HDR10、HDR10+、Dolby Vision、VFR 和隔行片源另行设计流程，不能靠增加几个标签变成正确输出。

HDR 也不能一概填写相同的 PQ、色彩原色和亮度值。`master-display` 描述母版显示设备的色域与亮度，`max-cll` 描述内容亮度信息；没有取得对应信息时，不应从通用命令中复制示例数值，也不能因未看到 P3 字样就推断母版显示设备一定使用 BT.2020 原色。
