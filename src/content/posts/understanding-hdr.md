## HDR 改变了什么

**HDR（High Dynamic Range，高动态范围）**主要扩展画面能够表示的亮度范围，让高光、正常照明区域与阴影之间有更大的表现空间。与之相对的是 **SDR（Standard Dynamic Range，标准动态范围）**。

例如一个室内镜头，窗外的阳光、灯泡和金属反光可以明显亮于人物面部，同时保留高光的层次。HDR 的作用不是把整张画面统一调亮；夜景仍然可以很暗，也不是每部 HDR 电影都会频繁出现特别亮的画面。

最终看到多少细节，还取决于拍摄、母版、调色、编码与显示设备。HDR 标志本身不能证明一个版本比另一个 SDR 版本更好，更不能把普通 SDR 文件改个标记就还原出原本不存在的高光信息。

手机相机里的“HDR 拍照”常指多曝光合成等处理过程，成品可以仍然是 SDR 图片。这里讨论的是视频信号与播放链路中的 HDR，不能只凭同一个缩写就把两种用法混在一起。

## 亮度、色域、位深与分辨率

这些词经常同时出现，但回答的是不同问题。

| 概念       | 说明什么                                 | 常见标记                  |
| ---------- | ---------------------------------------- | ------------------------- |
| 动态范围   | 从暗部到高光可以表示多大的亮度跨度       | SDR、HDR                  |
| 色域       | 可以表示哪些颜色、范围有多大             | BT.709、P3、BT.2020       |
| 位深       | 每个分量用多少级数值表示，渐变能划分多细 | 8bit、10bit、12bit        |
| 分辨率     | 一帧画面有多少像素                       | 1920×1080、3840×2160      |
| 编码与容器 | 视频怎样压缩、轨道怎样装进文件           | HEVC、AV1；MKV、MP4、M2TS |

因此，**4K 不等于 HDR，HEVC 不等于 HDR，10bit 也不等于 HDR**。10bit SDR 很常见；HDR 与广色域常一起使用，但两者并不是同一个概念。

### nit 表示亮度，不是画质分数

亮度常用 **nit（尼特）**表示，`1 nit = 1 cd/m²`。传统 SDR 制作常以约 100 nit 的参考白为基础，但家里的 SDR 显示器不因此被限制在 100 nit；实际观看亮度还受显示设置和环境影响。

HDR 资料中的 1000、4000、10000 nit，可能分别在说母版监视器、内容中的亮度值，或信号系统的表示上限。**它们不能直接当成电视实际发出的亮度。**

看屏幕规格时，也要区分小面积高光、持续亮度与全屏亮度。黑位、局部调光、色域、色彩准确度和环境光都会影响效果，不适合用“低于某个峰值就完全不能看 HDR”划一条通用界线。

### BT.2020 不代表画面填满了整个色域

UHD HDR 视频常用 BT.2020 色彩信号，但很多电影的实际调色范围主要落在 P3 色域内。MediaInfo 里同时出现 `Color primaries: BT.2020` 和 `Mastering display color primaries: Display P3`，并不矛盾：前者描述信号标记，后者描述母版显示设备。

同样，屏幕接受 BT.2020 输入，也不表示它能显示 BT.2020 中的所有颜色。

### 10bit 与 12bit 不能只看数字大小

8bit 每个分量有 256 个码值，10bit 有 1024 个，12bit 有 4096 个。更多量化等级有助于减少渐变中的色带，但实际结果还受压缩、抖动处理和显示链路影响。

文件的编码位深、解码或内部运算精度、HDMI 输出位深、面板位深是不同层面。显卡输出显示为 12bit，不代表正在播放的 10bit 文件变成了原生 12bit 内容；杜比视界文件显示 10bit，也不能只凭这一项断定它是假的。

## PQ、HLG 与色调映射

视频保存的是数值，显示时要知道这些数值怎样对应亮度。**传递函数**就在这条转换关系中起作用。现行 [ITU-R BT.2100-3（2025）][itu-bt2100] 规定了两套 HDR 体系：PQ 与 HLG。

### PQ：按绝对亮度解释信号

**PQ（Perceptual Quantizer）**的显示端电光转换函数由 SMPTE ST 2084 定义，按人眼感知特性分配码值，对应绝对亮度，表示上限为 **10000 nit**。HDR10、HDR10+ 和常见的 Dolby Vision 发行格式都与 PQ 有关。

**10000 nit 是 PQ 的信号表示上限，不是某一种格式独享的能力，也不是播放设备的最低要求。** HDR10 并没有“最高只能到 1000 nit”的硬限制；实际内容可能按不同的母版条件制作，显示时再适配目标屏幕。

### HLG：为广播与不同显示条件考虑的另一套体系

**HLG（Hybrid Log-Gamma）**由 BBC 与 NHK 共同开发，采用与场景相关的信号表示方式，显示端根据峰值亮度与观看条件调整呈现，适合广播、直播等用途。[BBC 的 HLG 项目说明][bbc-hlg]介绍了它的设计。

HLG 的基本显示不依赖母版显示器参数或逐场景动态元数据。但这不等于“HLG 视频里不可能有任何元数据”；PQ 传递函数本身也不能与 HDR10 等格式的元数据要求混为一谈。

它对 SDR 的兼容性也有条件，涉及相同的色彩格式和正确的播放处理，不能理解成任何老电视、任何软件都能把 HLG 当普通 BT.709 SDR 文件正确显示。

### 色调映射：把片源亮度适配到屏幕

假设片源中的一些高光达到 4000 nit，而屏幕只能显示更低的亮度，就需要在保留层次与整体观感之间做处理。这通常称为 **Tone Mapping（色调映射）**；超出屏幕色域的颜色，还需要色域映射。

映射可能由播放器、操作系统或电视完成，也可能涉及多个环节。HDR 转 SDR 是其中一种用途，HDR 屏幕播放超出自身能力的 HDR 内容同样可能需要映射。

**正确的 HDR 转 SDR 是正常的播放方式。** 它不能让 SDR 屏幕拥有 HDR 屏幕的高光能力，但也不能一概说成“怎么转都不如 SDR”。与单独发行的 SDR 版本相比，结果还要看两版母版与调色、映射算法和实际观看条件。

## 常见 HDR 格式

下面按电影文件、UHD 蓝光和日常播放中会遇到的情况整理。表内写的是常见使用方式，不是每项标准的全部技术上限。

| 格式                         | 主要特点                                                    | 兼容性重点                                                     |
| ---------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------- |
| **HDR10**                    | 常见为 10bit、BT.2020、PQ，使用静态元数据                   | UHD HDR 与本地播放中常见的基础格式；转到 SDR 仍需正确映射      |
| **HDR10+**                   | 在 HDR10 基础上加入可按场景或帧变化的动态元数据             | 正确处理时可按 HDR10 播放；要利用动态元数据，链路需支持 HDR10+ |
| **Dolby Vision（杜比视界）** | 包含动态元数据与不同发行 Profile，可采用单层或双层结构      | 能否按 HDR10 播放取决于 Profile，不能仅凭 `DV` 判断            |
| **HLG**                      | 不依赖动态元数据的 HDR 体系，常见于广播、直播及部分拍摄设备 | 播放器与屏幕要正确识别 HLG；SDR 兼容有前提                     |

国内内容和设备上还会看到 **HDR Vivid**。[UWA 官方介绍][uwa-hdr]将其定义为动态 HDR 视频标准，也是需要片源、播放软件与显示设备相互配合的 HDR 体系。它与 Dolby Vision、HDR10+ 不是可以互换的标签，不能因为设备支持其中一种，就推断它支持其余格式。

[HDR10+ 官方 FAQ][hdr10plus-faq]确认了 HDR10 回退关系。这个“兼容”说的是格式基础关系，仍以播放器能正确处理相应编码、容器和信号为前提。

格式名称本身也不能排出一张适用于所有电影的画质排行榜。比较两个版本时，先确认是不是相同剪辑、相同母版和相近的编码条件，再看 HDR 格式与设备实现的影响。

## 静态与动态元数据

**元数据是描述视频或辅助显示处理的数据，不是画面本身。** HDR10 中常见的静态信息包括母版显示器参数与内容亮度统计；HDR10+、Dolby Vision 还可以携带随场景或帧变化的信息，辅助显示端适配。

| MediaInfo 常见字段                  | 大致含义                                 | 不能据此推断什么                             |
| ----------------------------------- | ---------------------------------------- | -------------------------------------------- |
| `Mastering display color primaries` | 母版显示器的色度信息                     | 不能直接当作每一帧实际使用的色域             |
| `Mastering display luminance`       | 母版显示器的最小、最大亮度信息           | 不等于影片最暗与最亮像素的实测值             |
| `MaxCLL`                            | 内容最大光级，描述整段内容的最高亮度信息 | 不等于屏幕播放时一定能达到的亮度             |
| `MaxFALL`                           | 内容中各帧平均光级的最大值               | 不是整部电影平均亮度，也不是每一帧的最高亮度 |

文件中这些字段可能缺失、为零，或填写得不准确。仅凭一个 `MaxCLL` 数字，不能判断发行质量，也不适合随手把所有文件统一改成 1000 或 4000。

“静态”是说片源携带的这类描述信息不按每个场景分别提供一套，**不代表电视或播放器只能从头到尾使用同一条映射曲线**。设备可以自行分析画面，再做动态色调映射；[mpv 手册][mpv-manual]中的峰值检测就有按场景映射的说明。

反过来，片源有动态元数据，也不代表所有设备都会利用它。电视自己分析 HDR10 的“动态色调映射”，与读取片源中的 HDR10+ 或 Dolby Vision 动态元数据，是两种不同的处理依据。

## 杜比视界的 Profile、BL、EL 与 RPU

**Profile**规定一类 Dolby Vision 码流的结构与兼容方式；**Level**约束分辨率、像素处理速率等解码能力。两者都不是画质排名，数字更大不代表画质必然更好。

先认识三个常见缩写：

| 缩写    | 名称                      | 在常见 HEVC 杜比视界片源中的作用                                                               |
| ------- | ------------------------- | ---------------------------------------------------------------------------------------------- |
| **BL**  | Base Layer，基础层        | 承载基础画面；是否能独立作为 HDR10 播放，要看 Profile                                          |
| **EL**  | Enhancement Layer，增强层 | 双层结构中的增强信息，不能简单等同于另一套动态元数据                                           |
| **RPU** | Reference Processing Unit | DIY 工具中通常指携带 Dolby Vision 元数据的相关数据单元或提取文件，用于画面重构与显示映射等处理 |

### Profile 5、7 与 8 的区别

下面只列本地影视整理中常遇到的几种结构。处理时还需结合实际码流与工具文档确认；[dovi_tool][dovi-tool]提供了常见数据组合与转换方式的说明。

| Profile         | 常见结构与用途                                     | 基础兼容关系                                             |
| --------------- | -------------------------------------------------- | -------------------------------------------------------- |
| **Profile 5**   | `BL + RPU`，单层，常见于流媒体，采用专门的色彩表示 | 不兼容 HDR10，不能删除 RPU 后直接当 HDR10 播放           |
| **Profile 7**   | `BL + EL + RPU`，双层，用于 UHD 蓝光发行           | BL 兼容 HDR10；完整 Dolby Vision 处理还涉及 EL 与 RPU    |
| **Profile 8.1** | `BL + RPU`，单层，具有 HDR10 兼容基础层            | 可以按 HDR10 播放；并不意味着它一定由 Profile 7 转换而来 |
| **Profile 8.4** | `BL + RPU`，单层，具有 HLG 兼容基础层              | 基础兼容对象为 HLG，不能按 8.1 的 HDR10 回退关系处理     |

Profile 8 还存在其他兼容类型。因此，看到 `Profile 8` 时，要继续看基础层兼容标记；不能把所有 Profile 8 都简称为“HDR10 加杜比元数据”。

Profile 5 如果被按普通 HDR10 / YCbCr 路径错误处理，可能出现明显的偏紫、偏绿等颜色问题。支持相应处理的软件可以正确转换或显示它，但这不等于文件本身具有 HDR10 向后兼容性。

### MEL、FEL 与“完整双层播放”

Profile 7 的增强层又常分为 **MEL（Minimal Enhancement Layer）**与 **FEL（Full Enhancement Layer）**。MEL 不提供 FEL 那样的有效图像残差信息；FEL 的残差会参与更高精度画面的重构。

这里有一个容易忽略的区别：**播放器使用 BL 和 RPU 显示出杜比效果，不足以证明它也解码并使用了 FEL 的图像残差。** 屏幕弹出 Dolby Vision 标志，同样不能单独证明这一点。

把 Profile 7 转成 Profile 8.1 时，常见流程会移除 EL，并对 RPU 作相应处理。如果源片是 FEL，这不是完整保留双层数据的等价复制；也不能用“视频没重新压制”就证明所有 Dolby Vision 信息都保留了。[dovi_tool 的文档][dovi-tool]区分了转换模式、EL 移除与 RPU 处理。

EL 也不是“把 4:2:0 文件无条件变成原生 4:2:2”的通用补丁。原始编码、杜比重构过程和最终输出格式需要分别看。

### 层数、轨道数与容器不是一回事

UHD 原盘与 MKV 可以用不同方式组织同一套 BL、EL 和 RPU。一个 MKV 里只看到一条视频轨，不意味着它只剩一层视频；单轨也可能承载双层杜比数据。

同样，`BL+EL+RPU` 描述的是码流组成，不能仅凭这几个字判断容器里的轨道数量。重新封装后需要结合轨道信息、工具报告与播放结果确认，不能只按扩展名判断“杜比是否保留”。

## 怎样读 MediaInfo

打开 [MediaInfo][mediainfo] 的文本或树状视图，先看编码、位深、色彩信息，再看 `HDR format`。下面都是为了讲解而写的简化示例，不对应某部实际影片；版本不同，字段文字也可能略有差异。

### HDR10 示例

```text
Format                       : HEVC
Format profile               : Main 10@L5.1@High
HDR format                   : SMPTE ST 2086, HDR10 compatible
Bit depth                    : 10 bits
Color range                  : Limited
Color primaries              : BT.2020
Transfer characteristics     : PQ
Matrix coefficients          : BT.2020 non-constant
Mastering display luminance  : min: 0.0050 cd/m2, max: 1000 cd/m2
Maximum Content Light Level  : 1000 cd/m2
Maximum Frame-Average Light Level : 400 cd/m2
```

`Main 10` 是 HEVC 编码 Profile，和 Dolby Vision 的 Profile 不是一套编号。`PQ` 与 `BT.2020` 描述信号特性；`HDR10 compatible`、母版与内容亮度信息则提供进一步线索。

其中的 1000 和 400 也不能读成“画面一直以 1000 nit 显示，平均为 400 nit”。后一项是各帧平均光级中的最大值。

### Dolby Vision 示例

```text
Dolby Vision, Version 1.0, dvhe.05.06, BL+RPU
Dolby Vision, Version 1.0, dvhe.07.06, BL+EL+RPU, Blu-ray compatible
Dolby Vision, Version 1.0, dvhe.08.06, BL+RPU, HDR10 compatible
```

这些字段可以这样拆开：

- `dvhe.07.06` 中，`07` 是 **Profile 7**，`06` 是 **Level 6**。
- `dvhe.08.06` 表示 **Profile 8、Level 6**，不是“Profile 8.6”。是否属于常说的 8.1，还要结合 HDR10 兼容标记等信息确认。
- `BL+RPU` 与 `BL+EL+RPU` 用来区分列出的数据组成；不能单靠它们断定 MEL / FEL 或实际播放路径。
- `HDR10 compatible` 表示具有相应的兼容基础，不代表电视当前就在以 HDR10 模式播放。
- `Version 1.0` 属于文件中相关配置的版本信息，不能直接拿它与产品名称 Dolby Vision 2 对号入座。

同一条视频报告同时列出 Dolby Vision 和 HDR10 compatible，或者同时含有几种 HDR 元数据，并不一定矛盾。先看它们共享的基础视频与兼容关系，而不是数一共有几个 HDR 标签。

### Limited 不等于低画质

`Limited` 和 `Full` 表示数值范围约定，不是画质档次。典型视频有限范围的亮度码值为 8bit 的 `16–235`、10bit 的 `64–940`；色度分量的范围另有定义，不能把亮度范围套给所有分量。

关键是输入、转换与输出各环节按正确约定处理。强行改为 Full 或错误解释范围，反而可能造成黑位抬高、暗部压死或高光裁切。

## 怎样才能播放 HDR

要让一部 HDR 影片最终以 HDR 显示，需要**片源、播放设备、播放软件、输出链路与屏幕相互配合**。这些环节可以集中在一台设备里，例如电视内置应用播放 HDR；也可以分布在电脑、功放和电视之间。并不是一定要另外购买播放器或盒子。

1. **片源确实带有 HDR 信息。** 本地文件先用 MediaInfo 确认 HDR 格式、视频编码和 Dolby Vision Profile，不能只看文件名里的 `4K`、`10bit` 或 `DV`。流媒体还要确认具体片名、订阅方案、清晰度设置，以及当前应用和设备是否能取得 HDR 版本；同一个片名在不同入口未必提供相同规格。
2. **屏幕支持准备输出的 HDR 格式。** 电视、显示器或设备内置屏幕需要接受对应的 HDR 信号；只有 4K 分辨率或广色域并不足够。想直接显示 Dolby Vision，还要确认屏幕支持 Dolby Vision；只支持 HDR10 的屏幕，需要片源具备 HDR10 回退条件，或由播放器正确转换为它能接受的格式。亮度、黑位和调光能力则影响实际效果。
3. **播放设备能够解码，并支持所需输出。** 电视内置播放器、盒子、UHD 蓝光机和电脑都可以承担播放任务，前提是支持对应编码、分辨率、帧率和位深。电脑还要看显卡、驱动及实际连接的输出端口；设备写着“支持 HEVC”或“支持杜比视界”，不代表所有 Profile、容器与播放方式都支持。播放实体 UHD 碟，还需符合影碟的读取与播放条件，见[蓝光读取与播放说明](/posts/understanding-blu-ray/#光驱能读不等于电影能播)。
4. **播放器与系统使用正确的 HDR 路径。** 软件需要识别片源的色彩信息与元数据，并按目标屏幕进行输出或映射。Windows 桌面 HDR 播放通常还需要在[“设置 → 系统 → 显示”][windows-hdr]中为目标屏幕启用 HDR，再确认播放器的 HDR 输出、直通或映射设置；具体操作随渲染器与版本而异。若软件已把视频转为 SDR，文件本身仍叫 HDR，并不表示屏幕此时收到的也是 HDR。
5. **外接链路能把信号送到屏幕。** 使用 HDMI、DisplayPort、USB-C 转接器或扩展坞时，要核对整条链路是否支持所选分辨率、刷新率、位深和 HDR 输出。中间经过功放、回音壁或切换器，也要确认其视频直通能力；电视对应输入口有时还需开启“增强格式”“HDMI 深色”等选项。线材按所需带宽与认证选择，不能仅凭“4K 线”三个字判断，也不是所有 HDR 播放都必须使用 HDMI 2.1。
6. **网络播放时，传输与转码方式也要合适。** NAS、网盘或流媒体播放需要足够且稳定的吞吐量，高码率原盘的瞬时需求可能高于平均码率。使用 Emby、Jellyfin、Plex 等媒体库时，可查看客户端是直接播放还是正在转码，以及转码输出是否仍为 HDR。NAS 如果只负责提供文件，解码与 HDR 显示由播放端承担，不需要因为存放 HDR 影片就额外配一块显卡。

例如，在电视上用内置应用播放，主要核对片源、应用和电视本身；用电脑连接电视，则还多出系统 HDR、显卡输出、线材和输入口设置。[Apple TV 的官方说明][apple-hdr]也明确要求逐项核对电视输入口、线材和中间设备。外接播放遇到问题时，可以先绕过功放或切换器，直连电视确认，再逐个接回，定位是哪一环不支持。

首次设置时，可以先用**格式明确的 HDR10 测试片或已知正常的 HDR10 片源**确认基础链路，再检查 HDR10+ 或 Dolby Vision。播放时同时查看播放器的输入与输出信息、屏幕的信号信息，确认接收的是预期格式；不要只用“画面变亮了”判断。播放设备若被设置为始终输出 HDR，也不能用屏幕的 HDR 标志反推片源一定是 HDR。

如果最终使用的是 SDR 屏幕，仍可通过正确的色调映射观看 HDR 片源，只是最终显示为 SDR，设置方式见前面的[色调映射说明](#色调映射把片源亮度适配到屏幕)。

## 能播放，到底支持到了哪一步

谈“支持 HDR / 杜比视界”时，至少应区分以下几个环节。

| 环节         | 实际要确认的事                                                       |
| ------------ | -------------------------------------------------------------------- |
| 读取文件     | 能否处理该 MKV、MP4、M2TS 或原盘结构                                 |
| 解码与解释   | 能否处理对应视频编码、Profile、位深与色彩表示                        |
| 使用附加数据 | 是否利用 HDR10+ / Dolby Vision 元数据，双层内容是否处理 EL           |
| 渲染与输出   | 是转成 SDR、映射为 HDR10，还是通过受支持的 Dolby Vision 输出路径播放 |
| 最终显示     | 系统、驱动、接口、功放与屏幕是否接受并正确显示该输出信号             |

“软件能读取 RPU”“画面颜色正常”“电视亮起 DV 标志”“完整还原 FEL”分别说明不同事情，不能互相替代。

例如，[mpv 当前手册][mpv-manual]包含 Dolby Vision / HDR10+ 元数据处理和色调映射选项；其中也明确说明，一种利用这些数据生成 HDR10 亮度信息的输出方式，**并不是把完整 HDR10+ 或 Dolby Vision 元数据发送给显示器**。因此，软件名称本身不是完整兼容性结论，具体版本、构建、渲染器和输出方式都要对上。

同理，电视内置流媒体应用支持某种 Dolby Vision，不代表 USB 播放同 Profile 的 MKV、外接盒子或电脑输出也获得了相同支持。

### 发灰、发暗与字幕刺眼，先查哪一层

- **画面发灰、饱和度不对**：检查 PQ、HLG 是否被按普通 SDR 解释，Profile 5 是否被按普通 YCbCr 路径处理，以及色域转换是否正确。
- **黑位偏高或暗部压死**：检查信号范围解释与输出设置，避免把 Limited / Full 简单理解成“低级 / 高级”。
- **整体偏暗或高光没层次**：检查系统 HDR 状态、屏幕模式、映射是否适合目标亮度，再结合母版和环境判断；不是所有暗场都需要人为提亮。
- **字幕明显比画面刺眼**：检查播放器的字幕白电平和合成方式。视频的 HDR 元数据不会自动替所有外加字幕做好亮度适配。

普通 SDR 截图也不能完整重现 HDR 屏幕的亮度范围。网上的并排截图最多说明某个转换后的结果，不适合单独作为格式画质排名的证据。

## DIY 时哪些信息不能随便丢

重新封装通常不重新编码视频，但容器、工具版本与操作方式仍可能改变 HDR 数据是否保留。动手前后，建议各留一份 MediaInfo 或 BDInfo 报告。

1. **记录源格式**：HDR10、HDR10+、Dolby Vision 的 Profile，是否包含 EL，以及色彩与亮度标记。
2. **明确目标设备**：它支持的编码、容器、Profile 与实际播放路径，尤其是否需要 HDR10 兼容基础层。
3. **封装后核对**：时长、帧率、轨道、HDR 元数据和章节是否符合预期；再检查字幕、音画同步与实际播放模式。
4. **转换时记下舍弃了什么**：去掉 RPU、去掉 FEL 或重新编码，不应都笼统称为“无损保留杜比”。

给另一版视频注入 RPU 时，不能只核对片名和分辨率。**剪辑、帧数、帧序、时间对应关系、裁切与有效画幅，以及基础画面的调色，都可能影响元数据是否匹配。** 同一部电影的流媒体版与蓝光版不一定可以直接互用；注入成功、MediaInfo 出现 DV 标签，并不证明画面正确。

重新压制视频也不能默认照搬原片的所有元数据。裁切、缩放、删帧、拼接、滤镜和调色都可能使原有信息失去对应关系，需要按具体工具与工作流程处理。

后续进行轨道提取、封装与 RPU 操作时，可从 [DIY 工具清单](/posts/media-diy-software/)进入相应工具文档，先用短片段确认结果，再处理完整影片。

## 近年的新名称怎么看

截至本文核对日期，HDR 的设备功能还在继续扩展。这里把容易与文件格式混淆的名称单独放在一起。

- **DisplayHDR / DisplayHDR True Black** 是 VESA 的显示器性能认证，和片源中的 HDR10、HDR10+ 不是同一种分类。当前测试框架为 CTS 1.2，**2026 年 7 月**又增加了 [True Black 1400 等级][vesa-1400]。认证还涉及黑位、全屏亮度、色彩等指标，不能仅凭“支持 HDR 输入”或标志中的一个数字推断完整显示能力，详见 [VESA 性能要求][vesa-displayhdr]。
- **HDR10+ Adaptive** 等功能会考虑环境光；**HDR10+ ADVANCED** 是进一步扩展的功能体系，官方于 **2025 年 12 月**公布，涉及亮度、运动处理等能力。[当前官方 FAQ][hdr10plus-faq]已记载 Prime Video 于 2026 年开始提供相关内容。具体片名、设备和可用功能，仍需查[官方说明][hdr10plus-advanced]与对应产品资料。
- **Dolby Vision 2** 是 Dolby 新一代图像技术体系的产品名称，已于 **2026 年 8 月**[在部分海信电视上推出][dolby-vision-2-launch]。它不等于 MediaInfo 中的“Profile 2”；已有 Dolby Vision 内容可以受益于新的显示处理，但全部新功能仍取决于内容、设备与固件，见 [Dolby 官方介绍][dolby-vision-2]。

整理现有 UHD 蓝光与媒体文件时，仍然要落回具体码流、Profile、元数据与播放链路，而不是只更新文件名中的标签。

继续处理时可看：[章节的处理](/posts/media-chapters/)，从提取章节、补充名称和调整时间，继续到重新封装与播放检查。
