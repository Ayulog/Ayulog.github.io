PT 相关工具经常出现在同一份教程里，但解决的问题并不相同。下载器负责传输和做种；Vertex 负责订阅与任务管理；IYUUPlus 侧重已有资源的跨站辅种和下载器间转移；PTtool 则处理文件硬链接。先分清这些关系，再决定要装哪些。

本文依据项目说明与官方文档整理，资料核对于 **2026 年 10 月 9 日**，属于选型与使用思路记录。具体部署参数、站点支持和客户端兼容性，以准备安装的版本为准。

## 先看各自负责什么

| 工具                       | 主要用途                                                     | 什么时候需要                                     |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------------------ |
| qBittorrent / Transmission | 下载、校验文件、持续做种                                     | PT 下载的基础环节，先选一个配好                  |
| PTtool                     | 按文件大小复制或建立硬链接，保留做种目录                     | 想整理媒体库，又希望下载目录继续做种             |
| Vertex                     | RSS 订阅、筛选与推送任务，管理下载器和相关规则               | 手动添加、筛选和管理任务开始变得繁琐             |
| IYUUPlus                   | 根据已有种子查询跨站匹配、辅种，以及在下载器之间转移种子任务 | 已积累一批资源，希望复用数据继续做种或调整下载器 |

可以把它们理解成围绕下载器工作的几组配套工具：Vertex 决定添加哪些任务，IYUUPlus 查找已有资源还能在哪里做种，PTtool 为媒体库建立文件入口。实际传输与文件校验仍由下载器完成。

这里还有三个容易混淆的词：

- **做种**：下载器保留任务，并向其他用户上传已有数据。
- **辅种**：为其他匹配的种子任务复用已有数据，校验通过后继续做种。
- **硬链接**：给同一份文件数据增加一个目录入口，用于文件整理；它本身不会添加任何种子任务。

所以，建立硬链接不等于完成辅种；在其他站点找到同名资源，也不代表本地文件一定能通过校验。

## 下载器：qBittorrent 与 Transmission

[qBittorrent](https://www.qbittorrent.org/) 和 [Transmission](https://transmissionbt.com/) 都是 BitTorrent 客户端，也是后面这些工具连接的基础。先把下载器的保存目录、远程管理入口、账号和任务状态弄清楚，再接自动化工具，排错会容易很多。

如果准备以 Vertex 管理 PT 任务，可以优先看 qBittorrent。Vertex 的[下载器文档](https://wiki.vertex-app.top/zhu-yao-mo-kuai/xia-zai-qi)明确说明优先适配 qBittorrent；Transmission 虽然可以接入，但不支持 Vertex 所说的刷流与自动删种，不能默认两者接入后的功能完全一致。

如果已经稳定使用 Transmission，也没有必要只为尝试辅种而换下载器。IYUUPlus 官方文档列出了对 qBittorrent 和 Transmission 的支持，可以先围绕现有环境配置。

选择版本时还要看所在 PT 站点的客户端要求。管理工具能够连接某个版本，不等于站点允许使用这个版本；已有任务也应先确认能正常下载、校验和做种。

## PTtool：保留做种目录，整理媒体文件

项目入口：[appotry/PTtool](https://github.com/appotry/PTtool)。

这个仓库既收集 PT 工具与教程，也提供自己的硬链接脚本。最实用的场景，是**下载目录保留原来的名字和结构，媒体库目录使用方便识别、刮削的名字**。

例如一部影片下载完成后，qBittorrent 继续使用原下载目录做种；整理工具在媒体库目录建立硬链接，再让 Emby 扫描媒体库。对于成功建立硬链接的大文件，两个入口指向同一份文件数据，不需要因为整理再完整复制一次。

### 几个脚本的区别

| 脚本          | 用途                                                          | 使用前需要留意                                                                   |
| ------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `mklink.sh`   | 对源目录和目标目录执行一次整理                                | 官方建议用于尚未建立链接的新目录，不把它当作增量同步工具                         |
| `dirlink.sh`  | 按源目录下的子目录处理，并用 `islinked.lk` 标记跳过已处理目录 | 文件需要放在子目录中；之后追加的文件不会因为已有标记而自动补齐                   |
| `autolink.sh` | 配合 qBittorrent 下载完成后运行外部程序的功能，触发整理       | 按说明修改目标目录，与 `dirlink.sh` 放在同一目录，并确认下载器运行环境能执行脚本 |

项目采用按大小分流的思路：大文件建立硬链接，小文件复制，方便媒体库单独修改 NFO 等元数据。当前脚本的默认阈值配置为 `FILEGIG=1000000c`，对应 1,000,000 字节。本次核对的 `dirlink.sh` 使用严格大于与小于判断，恰好等于阈值的文件不在这两组中，检查整理结果时要留意遗漏。

**这里按大小判断，并不是按扩展名识别 NFO 或图片。** 不能据此认为所有元数据都会独立复制。第一次运行时，先用少量已经下载完成的文件检查目标结果和日志，再接入自动执行。

### 硬链接能做什么，不能做什么

硬链接需要源文件与目标位于同一个文件系统，容器内的挂载方式也必须允许建立链接。放在同一台 NAS，甚至同一块硬盘上，都不足以保证这一点；不同文件系统、子卷或独立挂载边界仍可能阻止操作。

硬链接建立后，可以在媒体库侧修改文件名，而不改变下载器使用的那个文件名。但**原地修改文件内容，会影响所有指向这份数据的硬链接**。转码、重新封装、写入内嵌字幕或修改媒体标签时，应另存为独立文件，避免破坏做种数据。

删除一个硬链接入口，也不等于删除其他入口。下载器删除原下载路径后，只要媒体库仍保留硬链接，数据占用的空间通常就不会释放；这也是“已经删种，磁盘空间却没回来”的一个常见原因。

PTtool 解决的是文件整理问题，不会自动完成跨站辅种，也不等于完整的媒体识别和刮削系统。如果已经使用其他工具整理同一批文件，应先确定由谁负责整理，避免两套流程重复处理。

## Vertex：集中管理订阅和下载任务

入口：[Docker Hub 镜像 `lswl/vertex`](https://hub.docker.com/r/lswl/vertex)、[项目仓库](https://github.com/vertex-app/vertex)、[官方 Wiki](https://wiki.vertex-app.top/)。

Vertex 面向 PT 场景提供订阅和任务管理。它可以连接下载器，结合 RSS、筛选规则和任务管理功能，把“看到资源、判断是否需要、添加下载、管理后续任务”串起来。

对于经常手动检查 RSS、重复设置下载条件的人，这类工具能减少重复操作。它与 PTtool 的工作位置不同：Vertex 主要管理任务，PTtool 主要整理已经落盘的文件。需要媒体库时，还要安排识别、刮削与播放环节。

Vertex 官方也提供[追剧配置流程](https://wiki.vertex-app.top/pei-zhi-liu-cheng/zhui-ju-pei-zhi-liu-cheng)，包含选种、下载后建立软链接和媒体服务扫描。这里的软链接依赖原目标路径，与 PTtool 的硬链接机制不同；启用时先确认与现有整理工具的分工。

### 接入时先控制自动化范围

建议先连接一个下载器，用一个 RSS 订阅和简单规则，确认任务能进入预期分类、保存到正确目录，再逐步增加条件。

自动添加和自动删除应分开配置。尤其开启删种规则前，要弄清楚它操作的是任务还是连同数据一起删除，以及是否会影响其他任务或媒体库。站点的最短做种时间、H&R 等要求，也需要纳入自己的保留策略。

如果 Vertex 与其他工具共同连接同一个下载器，可以用分类、标签或规则划定各自管理的任务。避免多个工具同时决定同一批任务的移动、删除和整理。

### 当前维护状态

截至本文核对时，官方 README 和镜像说明均写明：**Vertex 已处于不新增功能、仅做问题修复的状态。** 这不等于完全停止更新，但选型时应以现有功能为依据，不把未来新增适配作为前提。

官方[安装说明](https://wiki.vertex-app.top/xin-shou-ru-men/an-zhuang-cao-zuo)使用 `lswl/vertex:stable`，持久化容器目录 `/vertex`，默认 HTTP 端口为 `3000`。实际部署前再核对标签与架构；通知渠道和站点适配同样需要看当前文档，旧教程里的功能未必仍按原方式维护。

## IYUUPlus：给已有资源辅种与转移任务

入口：[IYUU 官网](https://www.iyuu.cn/)、[IYUUPlus 开发版仓库](https://gitee.com/ledc/iyuuplus-dev)、[官方文档](https://doc.iyuu.cn/)。

IYUU 的核心是根据种子特征查询跨站匹配关系，IYUUPlus 则提供 Web 管理界面，把下载器、站点设置和计划任务接起来。对已经保存了不少资源的人，它的价值是让已有数据继续发挥作用。

### 自动辅种怎么工作

按[官方原理说明](https://doc.iyuu.cn/guide/what-is-iyuu)，流程大致是：

1. 读取下载器中的已有种子信息。
2. 向 IYUU 服务查询其他支持站点上的匹配种子。
3. 根据配置的站点凭据，把匹配任务交给下载器。
4. 下载器校验本地数据，校验通过后继续做种。

资源匹配成功，只是找到可尝试辅种的任务。文件名、目录层级、缺少的小文件或不同版本的内容，都可能影响校验结果。**不要用跳过校验来处理路径或文件不匹配的问题**；先确认任务指向的数据确实正确。

辅种也不保证一定产生上传量，后续还取决于站点上的下载需求。工具能够自动查找和添加任务，最终能否正常做种仍要看站点支持、账号状态和校验结果。

配置时需要填写对应站点要求的凭据，可能包括 Passkey、UID 或 Cookie。[站点文档](https://doc.iyuu.cn/guide/site)当前还说明，完整使用需要绑定合作站点，准备部署前先核对自己是否具备相应条件。IYUU 的 Token 与各 PT 站点的 Passkey 也不是同一个东西。

### 自动转移不会搬动资源文件

IYUUPlus 的[自动转移](https://doc.iyuu.cn/guide/transfer-torrent)，是把种子任务交给另一个下载器，并按规则转换保存路径。这里转移的是种子任务，**实际下载的数据不会随之复制或搬家**。

例如，原下载器看到的数据目录是 `/downloads`，目标下载器看到的是 `/data/downloads`。只有这两个路径确实对应同一份已有文件时，路径转换才有意义。换成另一台没有这些数据的机器，仅修改路径文字不会让文件自动出现。

转移时先保留来源任务，用少量种子验证目标下载器能找到文件并通过校验，再决定是否停止或清理来源任务。目标任务进入“下载中”时，也要先检查是否误指向了空目录。

### 两类目录要分清

| 目录类型           | 保存的内容                                                                           | 谁需要访问                                                |
| ------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| 资源数据目录       | 实际下载的影片、音频等文件                                                           | 执行下载、校验和做种的下载器；整理工具按需访问            |
| 下载器种子文件目录 | `.torrent` 等任务元信息，例如 qBittorrent 的 `BT_backup`、Transmission 的 `torrents` | 使用 IYUUPlus 自动转移时，IYUUPlus 需要能读取来源种子文件 |

IYUUPlus 普通辅种流程通过下载器接口工作，不要求把整块资源数据盘挂进自己的容器。使用自动转移时，才需要按官方说明配置可读取的来源种子文件目录；**这个目录不能用下载完成目录代替**。

### 安装与更新看当前文档

[官方快速开始](https://doc.iyuu.cn/guide/getting-started)使用 `iyuucn/iyuuplus-dev:latest`，并分别持久化 `/iyuu` 与 `/data`。这里的 `/data` 是 IYUUPlus 容器内部用于数据库的目录，不是下节示例中的媒体数据目录。

源码目录和数据库目录应分别保存，备份时也要一起考虑。应用源码更新与 Docker 镜像更新是不同层面的操作，具体升级、迁移方式按[官方更新说明](https://doc.iyuu.cn/guide/qa-iyuuplus-update)执行，不能只套用旧教程里的重新拉取镜像步骤。

辅种计划任务也不需要频繁轮询。官方建议每天运行一次并错峰，部分站点另有每日数量限制；先沿用合理的默认值，观察日志与实际结果后再调整。

## 目录与容器路径怎么规划

下载、做种和媒体整理能否配合好，很大程度上取决于目录是否清楚。以本地硬盘为例，可以先建立这样的结构；下面仅表示媒体数据布局：

```text
media-data/
  downloads/       # 下载器保存原始文件，继续做种
    movies/
    tv/
  library/         # 整理后的媒体库，供 Emby 等扫描
    movies/
    tv/
```

让需要建立硬链接的整理程序，在同一个挂载入口下访问源和目标，例如 `/data/downloads` 与 `/data/library`。下载器和整理程序尽量采用一致的容器内路径，可以减少路径转换；两个目录仍须位于支持硬链接的同一文件系统内。

应用配置另行保存，避免混进媒体目录：下载器、Vertex 和 IYUUPlus 各自持久化自己的配置与数据库。不同容器中的 `/data` 可以有完全不同的用途，挂载时看清楚宿主机目录和容器内目录两端。

下载器 API 地址与文件路径也是两回事。管理工具连接成功，只能说明它能访问接口，不能证明目标文件存在、具备权限或可建立硬链接。Docker 容器里的 `localhost` 指容器自身；连接其他服务时，要填写从当前容器能够访问的地址。

账号、Cookie、Passkey 和 Token 放在自己的配置里，截图或分享日志前清理这些内容。管理界面通过可信内网或私有组网访问，配置备份也按包含凭据的文件保管。

## 按需求搭配，逐步开启自动化

不需要一次把所有工具装齐，可以从当前遇到的问题开始：

| 当前需求                       | 可以先尝试的组合                           |
| ------------------------------ | ------------------------------------------ |
| 手动下载、长期做种             | 一个配置稳定的 qBittorrent 或 Transmission |
| 做种文件想同时进入媒体库       | 下载器 + PTtool，再由媒体工具识别与刮削    |
| 订阅和任务太多，手动管理繁琐   | qBittorrent + Vertex                       |
| 已有资源较多，希望跨站辅种     | 现有下载器 + IYUUPlus                      |
| 需要同时管理订阅、辅种和媒体库 | 先明确任务与整理归属，再按需组合上述工具   |

第一次串联时，选少量文件完整走一遍：下载完成、校验正常、整理后的文件可以播放、原任务继续做种，辅种或转移任务也能找到正确数据。确认这些结果后，再增加订阅数量和自动化规则。

如果还需要把后面的 Emby 入库、播放与远程访问接起来，可以继续看 [DebNAS 自动观影流程](/posts/2026-10-09-debnas-media-workflow/)。这篇先把 PT 这一段的工具分工和目录关系记清楚，后续具体部署再单独补配置与实际使用记录。
